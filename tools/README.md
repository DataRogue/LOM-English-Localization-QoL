# LOM_Localization/tools

## Where the text lives (0.5: workspace, base_ref, publish)

LOM_UI_EN ships **only this mod's own work**. The OverLlm English patch
(github.com/joshfreitas1984/LegendOfMortalOverLlm) is a separate mod: the plugin detects it and lays our
revisions over its installed files at run time, and none of its text is in the plugin folder except inside our
own revised lines, which ship as whole lines (owner ruling), and our **reviewed** lines. Owner ruling 2026-09-24: the mod
must be playable without OverLlm, so every line gets a line-by-line review pass, and a reviewed line ships even when its
text stays identical to OverLlm's line ("duplicate lines at this stage are fine"); a line neither reviewed nor revised
still does not ship. The **review ledger** (`ledger.py`, below) lists the reviewed lines. Three places:

| Place | Path | Holds | Shipped? |
|---|---|---|---|
| **workspace** | `LOM_Localization/workspace/` | the full working `translation/StringTable.csv` and `translation/scene/scene_text.txt`, our own `translation/scene/resize/*.resizer.txt` (if any), `strings/*.csv` (full review notes), `rules/*.json` (with their comments), `sentinels.json`, `base_ref.lock`, `translation/revision_record.tsv` (per revised row, what it was revised against, and for rows a build recorded while a dump was installed that dump's md5 as a fifth field; written by publish.py only), the review ledger `translation/reviewed.tsv` (table keys) and `translation/scene/reviewed_scene.tsv` (scene lines by raw key, and `resize/<file>`; written by ledger.py only) | never |
| **base_ref** | `LOM_Localization/base_ref/` | the OverLlm release the workspace diverged from (`StringTable.csv`, `_AutoGeneratedTranslations.txt`, `resize/` = its resizers, `README.txt`, `base_ref.json`), `game_source.tsv` (the game's own Chinese per key, from the harness `srcdump`) when present, and `history/NN-<stamp>/` (each earlier release the workspace was aligned with, kept by `rebase`) | never |
| **plugin** | `BepInEx/plugins/LOM_UI_EN/` | what `publish.py build` derives: workspace minus base_ref, plus the reviewed lines, rules without comments | yes (never `harness/`) |

- Every tool reads and writes the **workspace** through `lom_paths.TABLE` / `SCENE` / `STRINGS_DIR` (full
  tables, so the tools work as before); layout rules are edited in `lom_paths.WS_RULES_DIR`
  (`workspace/rules`). `lom_paths.assert_writable()` allows only the workspace table and scene file
  (`lom_paths.assert_ledger_writable()` only the two review ledger files, for `ledger.py`). After a
  `--live` write each apply tool calls `lom_paths.publish()`, which runs the build in process, prints one line,
  and exits **3** when nothing was published (a hand-edited shipped file, a check failure, an interrupted
  write) or **4** when the files were written but their check fails. Each apply tool (and `scene_hygiene.py`) takes
  `--keep-record KEYS|@FILE|all` and passes it to that publish (`publish.py build --keep-record`, below).
- **`publish.py build`** writes the plugin's
  - `translation/StringTable.csv` (rows whose value differs from base_ref, and every row the review ledger lists whatever
    its value, `key,"value"`, CRLF, no BOM),
  - `translation/StringTable.meta.tsv` (the revision record the fallback mode reads: a header line
    `# LOM_UI_EN revision record v1 game=<game build id or unknown>`, then one line per shipped row,
    `key TAB TextHash(the game text it was revised against) TAB TextHash(the OverLlm line it was revised against)`,
    `-` when not recorded). A row keeps the hashes recorded when it was revised: build keeps the record of every
    row whose shipped value is unchanged (`workspace/translation/revision_record.tsv` holds the hash of the value
    each record is for) and records only new or changed rows, from `base_ref/game_source.tsv` and base_ref. It
    saves the record in the workspace before it ships anything. A row whose text changed is re-recorded: the edit
    counts as a revision for today's game text and OverLlm line. When such a row was **out of date** (its old record's
    game-text hash is not `base_ref/game_source.tsv`'s: the game text changed since it was revised, and a term or name
    pass, a typo fix or any other edit touched it), build says so (a `WARNING revision record` line naming them, also
    through the apply tools' publish) and lists those rows with the record they had in
    `backups/rerecord-<stamp>/rerecorded_out_of_date.tsv` (next to a copy of the record it replaces). The default stays
    the re-record; `--keep-record KEYS|@FILE|all` keeps the old record of the changed rows among them instead (the
    plugin's fallback then keeps seeing the game update: OverLlm's newer line, or the row reported as out of date), in
    the same build (`@FILE`: one key per line, or a `game_text_changed.tsv`), and `--keep-record @` that listing brings
    back the records an earlier build replaced (only where the workspace still holds the record that build wrote).
    `check` says how many rows the next build would re-record out of date. The workspace record also carries, for the
    rows a build recorded while a dump was installed, a fifth field: the dump's md5 (first 12 hex digits), so `source`
    can tell the rows revised since that dump was installed (it is not in the shipped meta; a record without any stays
    in the four-field form). Only `source --restamp` changes an existing record of an unchanged row, and
    `--keep-record` with a listing as above (see below). When `workspace/translation/revision_record.tsv` is missing, build recovers it from the target's
    shipped `StringTable.meta.tsv` and `StringTable.csv` (as publish.py wrote them, checked against
    `.publish_state.json`) for every row whose shipped value is the workspace's, and says how many rows it
    recovered; rows new or changed since that publish are recorded as usual. If any shipped row cannot be
    recovered (the shipped files are missing, were edited, or the target was never published into) it refuses
    (exit 2) and writes nothing; restore the record from a backup, or pass `--rerecord` to record those rows
    afresh from today's game text and OverLlm line (the fallback then no longer sees a game update made since
    they were revised). What it recovered or recorded afresh is printed only once the record is saved (a build that
    refuses afterwards, e.g. over a hand-edited shipped file, says nothing about it); a recovered record has no fifth
    fields,
  - `translation/scene/scene_text.txt` (our changed or added lines and every line the scene ledger lists, byte for
    byte, one `key=` removal line per base_ref line we deleted, and an explicit line for any trimmed-variant key whose
    winner would otherwise depend on load order),
  - `translation/scene/resize/*.resizer.txt` (our own resizers from the workspace; a copy of one of OverLlm's only
    when the scene ledger lists it, `resize/<file>`: for playable layout without OverLlm the maintainer copies
    OverLlm's three resizers into `workspace/translation/scene/resize/`, reviews them and lists them),
  - `translation/MANIFEST.json` (format `overlay-1`: counts, base_ref md5s, sentinels as SHA-1 hashes only, no
    time stamp; with a review ledger also `reviewed_table`, `reviewed_scene`, `reviewed_same_as_overllm` (and its
    `_table` / `_scene` parts), `reviewed_resizers`, `reviewed_resizers_same_as_overllm`, and `standalone`
    {table_rows, table_total, scene_lines, scene_total}: what ships against the full working copy; the plugin plays a
    layer without OverLlm, and says so, at 98%. The asset rows TextFont, Image_* and TextMeshFont_* are skipped by
    TextTable.Load and never ship, so the ledger refuses them),
  - `strings/*.csv` (notes stripped of quoted OverLlm and on-screen wording),
  - `rules/*.json` (the workspace rules without `//` comments, `"comment"` fields or other fields the plugin's
    rule loader does not read; the field list is read from `src/LOM_UI_EN/LOM_UI_EN.cs`),
  - `THIRD_PARTY_NOTICES.txt` from `src/LOM_UI_EN` when that file exists,
  and removes the 0.4 copies of OverLlm's resizers and `profiles/`. If a shipped file was edited by hand since
  the last publish (`translation/.publish_state.json`), build refuses unless you pass `--force`, which first
  copies everything it overwrites or removes to `backups/publish-force-<stamp>/`. The state records the
  pending hashes before any file is written, so an interrupted publish is finished by the next build. A build
  with nothing to change writes nothing. Its summary counts the reviewed rows and lines that equal OverLlm's apart
  ("N reviewed, same as OverLlm"); the revision record (`StringTable.meta.tsv`) covers every shipped row, reviewed
  ones included. A reviewed row or line equal to OverLlm's line is still OverLlm's wording to the note cleaner and the
  text scan (only revised and added text counts as this mod's own there), so both stay as strict as without the ledger.
- **`publish.py check`** fails (exit 1) when:
  - base_ref overlaid with the shipped files differs from the workspace in any way (the TextTable map; the
    XUnity map with removals, trimmed variants and known values, exactly as `SceneDictionary.LoadOverlay`
    builds it);
  - a workspace scene line is one the loader rejects (it would silently remove OverLlm's line);
  - a shipped row or line equals base_ref's, or the installed OverLlm files', for the same key, and the review ledger
    does not list it (a listed one may equal OverLlm's); a shipped resizer is a copy of OverLlm's (or holds its lines)
    and the scene ledger does not list it (`resize/<file>`), or differs from the workspace's;
  - the review ledger lists a key the workspace does not have (a table key; a scene raw key that no loadable
    workspace line with English is written with; a resizer not in `workspace/translation/scene/resize/`), a listed scene
    line is not the line its key loads from (a later workspace line for the same key, written with another raw key,
    overrides it), or a listed row, line or resizer is not shipped with the workspace's text (checked on the shipped
    files alone, as the plugin serves them without OverLlm); `ledger.py missing` lists those keys; a damaged ledger (not `key TAB pass TAB date`, a repeated key, not sorted, a CR or a
    BOM) stops check and build;
  - a shipped file differs from what `build` would write now, or a publish was interrupted;
  - there is an unknown file under `translation/`, `strings/` or `rules/`, or a copy of an OverLlm file;
  - any text file in the plugin folder (`harness/` aside) holds a whole OverLlm value of 12+ characters or a run
    of 4+ words that only OverLlm's text has (not our own shipped text; OverLlm's text = base_ref, its history
    and the installed files); keys count only where we add them. Files are read as UTF-8 (stray bytes
    replaced), UTF-16/32 with a BOM or UTF-16 without one; one pass per file, stopping at its first 20 hits (a
    full copy of OverLlm's table is found in about a second);
  - the folder holds a binary file other than the plugin DLL and the sprites (a zip, gzip, a raw compressed stream
    or anything else that cannot be read as text). `LOM_UI_EN.dll` counts only at the folder's root and only as a
    well-formed PE file (a .NET assembly) with nothing after its last section; `sprites/*.png` only as a
    well-formed PNG: the signature, a chunk walk with every CRC right, IHDR first, only the chunk types a sprite
    needs (no `iCCP`, `eXIf` or private chunks, which could carry anything), image data that inflates to exactly
    the size IHDR gives, and IEND last with nothing after it; the text of its `tEXt`/`zTXt`/`iTXt` chunks is
    scanned like any text. It also fails on any other file over 16 MB, a link or junction, and a folder or file
    that cannot be opened: the folder is walked by long paths (`\\?\`), so a path over 260 characters or a name
    ending in a dot or a space is scanned, never skipped. The scan guards against *accidental* inclusion (a stray
    copy, a backup, an archive left in the folder), not against someone hiding OverLlm's text on purpose: data put
    in the chunks a well-formed sprite may carry (`PLTE`, `tRNS`, `sPLT`, `tIME` ... of any size, or plain text as
    uncompressed pixel data), a zip appended to the DLL behind its certificate-table entry or a grown last section,
    an NTFS alternate data stream (`README.txt:name`), UTF-16 text after 64 KB of clean text, base64 of an archive,
    or `\uXXXX` escapes in a `.txt` or invalid `.json` file all pass. Those evasions are accepted as out of scope
    (2026-09-24); the DLL's embedded resources are not scanned either;
  - the workspace revision record is missing (the failure says what `build` will do about it);
  - a strings note still names or quotes the row's OverLlm wording (an independent test, not a rerun of the
    cleaner), an override holds a `[...]` placeholder, or an override is OverLlm's own line of more than 3 words;
  - the shipped rules are not the workspace rules minus their comments.
  It warns (does not fail) when `harness/` holds anything besides `cmd.txt` and an empty `out/`: `harness/` is
  not scanned and must never be packaged. It reports the
  cross-file exact copies (table rows equal to an OverLlm scene value and the reverse) as info; they are ruled
  our revisions.
- **`publish.py rebase NEW_DIR`**, for a newer OverLlm release: the workspace becomes the new release with our
  revisions applied, and base_ref becomes the new release. It keeps ours where OverLlm changed a row we
  also revised, and lists those rows. It refuses a "release" that holds our own edits (a sentinel with our
  pre-0.4 text), and asks for `--allow-converged` when more than 20 of our revisions would become equal to it.
  Back-ups go to `backups/rebase-<stamp>/`; the new base_ref and workspace are staged first and swapped in, and
  `workspace/base_ref.lock` ties the two together, so a torn rebase or restoring only one of them is refused.
  Reviewed rows and lines (the ledger's) are kept like revisions, the ones still equal to OverLlm's line included (they
  never count as "converged"): where the new release changed one, the reviewed text is kept and listed among the
  conflicts (`review ledger: ...` says how many), so the ledger stays true of what ships; take the new line over by hand
  where it is better.
  The rows it keeps keep their revision record (the OverLlm line they were revised against), and it lists the
  rows whose new OverLlm line is not that line: for these rows the plugin's fallback serves OverLlm's line once
  the game text changed since the revision, while the revision record is trusted (under 70% of sampled rows
  changed; all of them in the backup's `rebase_fallback_rows.tsv`). The replaced release moves to
  `base_ref/history/`, so its wording stays known as OverLlm's (the note cleaning and the text scan use every
  earlier release too; `base_ref/history/` is written, read and removed by long paths, so a deep staging root does not
  hit the 260-character limit). Rows changed since the last build are recorded as build records them (out-of-date ones are
  said and listed in the backup's `rerecorded_out_of_date.tsv`; `--keep-record` as for build). Run `build` afterwards.
  From the OverLlm patch's `llmkit-upgrade` on (release 2026.09.28 on), a release has one table per game file in
  `Mods/English` (and its own BepInEx 5 plugins) instead of `StringTable.csv`. `NEW_DIR` may then hold those tables, or
  its own `Mods/English` may (an unpacked release zip).
  They are read as the plugin reads them (`lashtables.py`) and kept in base_ref as one `StringTable.csv` with the
  same rows: line breaks come out in Binarizer's form, and the plugin compares hashes either way
  (`OriginalMod.SameText`). The converted file is in the backup (`new_release_StringTable.csv`). Such a release ships
  no `_AutoGeneratedTranslations.txt`, so base_ref keeps its own. `publish.py check` compares the shipped rows with
  the installed per-file tables when those are what `Mods/English` holds.
- **`lashtables.py`**: the OverLlm patch's table in either layout. `find(dir)` returns the per-file tables (the plugin's
  order, an older `StringTable.csv` next to them as `leftover`), the single file, or nothing. `read_per_file(files,
  crlf=False)` does `TextTable.LoadBase`: each file is read whole with a port of the plugin's own
  `CsvUtility.ParseFile` (`parse_file`; a quoted value may span lines), and the last row of a repeated key wins. Without
  a leftover the map is the plugin's own (the plugin reads a leftover too). The patch's `*.yaml` (prefab and code text)
  are not read. `single_text(map)` gives the map as one
  StringTable.csv, which `table_map` reads back to the same map in Binarizer's form (`binarizer_form`: each run of line
  breaks becomes one CRLF).
- **`publish.py source SRCDUMP.tsv [--restamp KEYS|@FILE|all] [--game-build ID] [--rerecord] [--keep-record KEYS|@FILE|all]`** takes a harness
  `srcdump` (the game's Chinese per key; `key TAB value` with `\\`, `\t`, `\r`, `\n` escaped): after checking it,
  it becomes `base_ref/game_source.tsv` (the previous dump, the workspace record and `base_ref.json` are backed up
  to `backups/source-<stamp>/` first), and it rebuilds. It never changes an existing record: records with no
  game-text hash yet (`-`, the first capture) are filled from the dump, and a row whose game text changed since
  it was revised keeps its recorded hash, which is exactly what makes the plugin notice the change. Those rows
  are printed and written to `backups/source-<stamp>/game_text_changed.tsv`, in two groups:
  `overllm_newer` (OverLlm's line changed since the row was revised: the plugin serves OverLlm's line, while the
  revision record is trusted) and `needs_revising` (no newer OverLlm line, or none at all: this mod's text is
  kept and the plugin reports it as out of date); rows whose placeholders the new game text no longer has are
  listed too (`overllm_placeholders`: the plugin serves OverLlm's line for them). It also says whether the plugin
  will trust the record (it distrusts the whole record when 70% or more of an even sample of rows differ).
  `--restamp KEYS` (comma-separated), `@FILE` (one key per line, or a `game_text_changed.tsv`, filtered or not)
  or `all` re-records those rows without a value change, from the dump and today's OverLlm line: a maintainer
  confirming a revision still fits the new text. Re-recorded rows stop falling back. The header's game build id
  is the installed game's (`Compat.Fingerprint`; `--game-build` names another).
  The rows **revised before this `source` ran**, since the dump it replaces was installed (a build recorded them
  against that dump: the record's fifth field; rows revised but not yet built count too), whose game text the new
  dump changes, are listed on their own: group `revised_before_source` in `game_text_changed.tsv` (not in the
  groups above) and `backups/source-<stamp>/revised_before_source.tsv`, with the exact command that confirms them
  as revisions for the new game text (`publish.py [--stage ROOT] source base_ref/game_source.tsv --restamp
  @.../revised_before_source.tsv`; filter a copy of the file first if some were not). Until then their record says
  they were revised for the old text, so the plugin serves OverLlm's newer line for them, or reports them as out of
  date, and a later OverLlm rewording would replace them. `--keep-record` works as for build.
- **After a game update** (and an OverLlm release for it, if there is one): take a new `srcdump` and run `source`
  with it **first, before revising anything**; `rebase` onto the new OverLlm release if there is one (before or
  after `source`: that order does not matter). **Then revise**: work through `game_text_changed.tsv`: re-revise a
  row (build records it against the new dump and today's OverLlm line, so it neither falls back nor counts as
  stale, and a later OverLlm rewording alone never replaces it), or, where the revision still fits the new text as
  it is, `source base_ref/game_source.tsv --restamp KEYS` (same dump again). A row left alone keeps falling back to
  OverLlm's newer line, or stays listed as needing revision. In short: run `source` first, then revise. A row
  revised before `source` ran is recorded against the old dump (the build that recorded it could only know that
  one), so `source` lists it in the `revised_before_source` group with the `--restamp @FILE` command to run for
  the ones revised for the new game text. A term or name pass over rows that are out of date (listed, not yet
  re-revised) re-records them as revisions for the new text unless it is run with `--keep-record` (build warns and
  lists them; `build --keep-record @backups/rerecord-<stamp>/rerecorded_out_of_date.tsv` undoes it).
- **The review ledger (`ledger.py`)**: `workspace/translation/reviewed.tsv` (table keys) and
  `workspace/translation/scene/reviewed_scene.tsv` (scene lines by their raw XUnity key as written in the workspace
  scene file, i.e. the text before the first unescaped `=`, escapes as written; and `resize/<file>` for a resizer in
  `workspace/translation/scene/resize/`). One entry per line, `key TAB pass-name TAB YYYY-MM-DD`, UTF-8 without BOM, LF,
  sorted by key (a key may hold a TAB: the last two TABs separate the fields). An apply tool records what a review pass
  reviewed with `ledger.add(keys, pass_name)` / `ledger.add(raw_keys, pass_name, scene=True)` (`ledger.scene_key(line)`
  gives a line's raw key, `ledger.resize_entry(name)` a resizer's entry; a key already listed keeps its first entry),
  reads it with `ledger.load()` (`(table, scene)`, each `{key: (pass, date)}`) and takes out a line a later pass removed
  with `ledger.remove(keys, scene=...)`; every write goes through `lom_paths.assert_ledger_writable` (only the two
  files, inside the workspace and the stage, no hard link) and is atomic. Command line: `python ledger.py [--stage ROOT]
  add table|scene PASS KEY|@FILE ...`, `remove table|scene KEY|@FILE ...`, `show`, `missing` (the listed keys the
  workspace lacks, which check fails on). A listed line ships whatever its text; take a line out of the ledger only
  when it was not really reviewed.
- **Never edit the plugin's `translation/`, `strings/` or `rules/` by hand.** Edit the workspace, then publish.
- **Staging:** `--stage ROOT` on publish.py (or `LOM_STAGE=ROOT` for any tool) moves plugin, workspace,
  base_ref, backups, the change logs and the tools' non-live output under `ROOT/`. A stage root may not be,
  hold or lie inside the game folder or `LOM_Localization`; in stage mode build writes only inside the stage.
  Every guard resolves paths first (`os.path.realpath`, and `os.path.samefile` where both exist), so an 8.3
  short name (`C:/PROGRA~2/...`), a junction or a link cannot pass for another folder; a stage whose folders
  resolve outside it and a build target that holds links or junctions are refused. Every tool's output folder
  goes through the same guards: the `--live` change logs (`lom_paths.log_dir`, `LOM_Localization/<name>` or the
  stage's `localization/<name>`), the non-live output (`lom_paths.staged_dir`), the backups (`backup_path`,
  `new_backup_dir`: `rebase-`, `source-`, `rerecord-`, `publish-force-`, `pre-0.5-`, `rolled-back-`) and each file written
  into one of them (`out_path`). A junction or link that would carry a write out of its folder, a `..` in a log
  name, or a hard-linked file at a name the tool writes is refused before anything is written.
- **`cutover_0_5.py`** is the one-time switch from the 0.4 layout. `--stage DIR [--dll PATH]` is a dry run
  into a copy (`--dll` puts the 0.5 build into the staged plugin); `--live` is the real run and refuses a
  plugin DLL older than 0.5.0. The preflight runs the whole cut-over in memory first (publish plan, its check,
  the folder conflicts), so a refusal leaves nothing behind. It backs up to `backups/pre-0.5-<stamp>/`,
  creates the workspace (with the logged data fixes: XUnity's own runtime lines removed, overrides equal to
  OverLlm's line removed unless they are short labels that change what the player sees, `[...]` placeholder
  overrides removed and listed in `retranslate.txt`) and base_ref, then runs build and check.
  `--rollback BACKUP_DIR` undoes it (use `LOM_STAGE` for a staged one), after which it can run again.
- **`migrate_standalone.py`** (the 0.4 migration) is superseded. Its commands and command functions refuse;
  its parsers (`idea_parse`, `table_map`, `repair_table`) are still imported by publish.py.

## Scripts

Maintained translation scripts, moved here from session scratchpads on 2026-09-22. Every path comes from
`lom_paths.py` (see its docstring). Since 0.5 `lom_paths.TABLE` / `lom_paths.SCENE` are the **workspace**
files, and they are the only files any script may write; `lom_paths.assert_writable()` enforces that. The
plugin folder is written only by `publish.py`. The OverLlm patch's installed files
(`Mods/English/StringTable.csv`, `BepInEx/Translation/en/Text/_AutoGeneratedTranslations.txt`) are read-only
(`lom_paths.BASE_TABLE` / `BASE_SCENE`).

- **publish.py** -- `build` / `check` / `rebase`, as described above. Reads the workspace, base_ref, and the
  installed OverLlm resizers (to check what it removes). Writes only the shipped files listed above, inside
  the target folder, plus `translation/.publish_state.json`. `rebase` writes the workspace table and scene
  (through `assert_writable`) and base_ref.
- **cutover_0_5.py** -- the one-time 0.4 -> 0.5 switch described above.
- **ledger.py** -- the review ledger described above (`add` / `load` / `remove`, `scene_key`, `resize_entry`, and a
  command line). Reads and writes only `lom_paths.WS_LEDGER` and `lom_paths.WS_SCENE_LEDGER`; `missing` also reads the
  workspace through `publish.Inputs`.

Every script does `sys.path.insert(0, "..")` and `import lom_paths` so it can be run directly from its
own folder, e.g. `python proof/extract_scenes.py <lua dir> <out dir> 1,2`.

## proof/ -- scene-by-scene proofreading pass

- **extract_scenes.py** -- reads: Lua story scripts (arg `lua dir`), `lom_paths.TABLE` (current English),
  a scratchpad `Files_Raw_StringTable.csv` (see "remaining scratchpad references" below, for Chinese source
  text). Writes: `p_NNN.json` proofreading chunks into the arg `out dir`. Builds proofreading batches: every
  `ch<N>_*` Lua script walked in order, cut into windows of 35 editable lines with 5 lines of context, plus
  `LegendInfo/Ch_<N>_*` chronicle entries chunked by key order.
- **apply_proof.py** -- reads: a workflow result JSON (arg), the `p_NNN.json` chunks dir (arg, for the old
  English/Chinese each id maps to). Writes: with `--live`, `lom_paths.TABLE` and `lom_paths.SCENE` (backed
  up first via `lom_paths.backup_path`) plus a change-log TSV under `LOM_Localization/<log name>`; without
  `--live`, staged copies + the same log under `LOM_Localization/staged/proof` (the stage's under LOM_STAGE). Applies verified proofreading
  rewrites (`table|<key>` ids) to the string table and mirrors them into any XUnity line carrying the same
  Chinese + old English. After a `--live` write it calls `lom_paths.publish()`, as all five apply tools do.

## names/ -- name-romanization sweeps

- **sweep_names.py** -- reads: `lom_paths.TABLE`, `lom_paths.SCENE`, and the scratchpad
  `Files_Raw_StringTable.csv` (Chinese source). Writes: `n_NNN.json` review batches into the arg `out dir`.
  Flags lines whose Chinese carries a character's bare given name or full name (from `Character/*` rows)
  while the English lacks the settled romanization -- catches the base 7B-model patch's word-for-word name

## hygiene/ -- scene-text data hygiene

- **scene_hygiene.py** -- reads: `lom_paths.SCENE` (the workspace scene file), an optional `--fixes` JSON (list of `{line, old_line, en, category,
  note}`; `old_line` must still match the file). Writes: with `--live`, `lom_paths.SCENE` (backed up first to
  `LOM_Localization/backups/scene_text.txt.<stamp>.bak`) plus `LOM_Localization/scene_hygiene/scene_hygiene_changes.<stamp>.tsv`;
  without `--live`, a staged copy + the same log under `LOM_Localization/staged/scene_hygiene`. It reads the file as
  SceneDictionary does, which splits the whole file at **every** CR and LF: a physical line (the file split at its own
  line breaks) holding a stray CR or LF whose split leaves two or more lines makes the run refuse (exit 2, naming the
  line; nothing written), as `publish.py build` refuses it, since one line whose line break lost its `\n` escape and two
  lines run together look alike and rewriting it as one line would drop the others' English; a stray break that leaves
  one piece (a CR at a line's end, a CR alone) is removed (`stray_line_break`; it loads the same). Removes lines whose key has Hangul and junk keys
  (`test`/`123`/`131231`, Unity object ToString names, bare Fungus tag fragments like `{size`). A line the loader rejects
  is removed when its key already has a line that loads (the loader uses that one, so players' text is unchanged) or
  when it holds no English to keep (no `=` on a key base_ref lacks, an undecodable key, a line base_ref has rejected too).
  Of a key with two or more rejected lines and no loadable one, the last rejected line with English is rewritten and
  the key's other rejected lines are removed (`unloadable_superseded`), so exactly one loadable line remains (two with
  different values would make the overlay differ from the workspace); any other rejected line, for a key base_ref has or
  a line this mod adds, is rewritten with its value escaped (`rewrite_line`), never removed, and the run refuses (writing
  nothing) when such a line cannot be written escaped (a `//` or a bad `\u` escape in the English, or no `=` on a key
  base_ref has). It applies the verified value rewrites, and refuses to write unless every output line decodes the way
  SceneDictionary loads it, with no stray line break left. `plan()` is what a run does and `describe()` says it in
  words: when `publish.py build` refuses a workspace with rejected lines or a stray line break, its message quotes
  `describe()`, line numbers included. `--keep-record` is passed to its publish.
  First run 2026-09-22 (see `LOM_Localization/scene_hygiene/`).

## scene_audit/ -- audit of the scene-only lines (2026-09-27)

The scene-only lines are the workspace scene lines whose Chinese is no row of the game's string table (the full pass's
definition, `fullpass/extract_all.py`). Most of them come from older game builds, so the audit first finds out which ones
the installed game can still draw, then reviews only those. Working files go to `LOM_Localization/scene_audit/` (not in git).

- **scan_game.py** -- reads the installed game (Mortal_Data, read only; UnityPy with its TypeTreeGenerator, as `nametips`)
  and writes `scene_audit/game_text.json`: every LeanLocalization CSV table by language (the harness srcdump misses the
  DiceHeader table, which only the story scene loads), the Simplified-only characters (zh-cn vs zh-tw text of the same
  key), every Chinese string in prefabs, scenes and data assets with its object path, and the string literals of the
  game's assemblies (their `#US` heaps). About a minute.
- **classify.py** `[--per 10] [--chars 1100] [--also CLASSES]` -- matches each scene-only line against that, the Lua
  scripts in `gamedata/lua` and the string tables the way `SceneDictionary` looks text up (exact, then with single line
  breaks and the space around them removed, and the pieces between rich-text tags). Dead lines: `simplified`, `internal`
  (flag and object names, the dev test panels), `junk`, and `not-in-game` (the Chinese is nowhere in the game: an older
  wording or removed text). Live lines: `table-variant` / `table-fragment` (a table row without its markup or with other
  line breaks: the fallback when the table layer does not answer), `dice-header` (the fallback of the strings overrides),
  `ui`, `data`, `code`, `lua`, `composed` (built at run time). Writes `scene_audit/classified.tsv` (every line) and
  `scene_audit/chunks/p_NNNN.json` + `manifest.json` (the live lines, with the row or override each should agree with,
  neighbouring rows, the story lines before a dice check, and the established English of the names in each line).
  `--also not-in-game` reviews the older wordings too. It refuses when the game changed since `scan_game.py` ran.
- **audit_workflow.js** -- args `{chunks: [{chunk, ids}]}` from the manifest. A Sonnet reviewer per chunk fixes only real
  errors (meaning, names, terms, consistency with its row or override, typos), a second call covers any line it left
  out, and a Sonnet refuter checks every rewrite. Keep the file LF-only.
- **apply_audit.py** `<journal.jsonl ...> [--live]` -- applies the accepted rewrites that pass the scene-line checks,
  by exact line match (the raw key is unchanged, so the ledger needs nothing), and writes the change log, the skipped list
  and the reviewers' notes about rows and overrides (`ref_issues.<stamp>.tsv`, not applied). `--live` backs up the scene
  file to `backups/` and publishes; run `publish.py check` afterwards.
- **rowfix.py** `chunks ISSUES.json` / `apply JOURNAL... [--arbiter FILE] [--live]` and **rowfix_workflow.js** -- the
  follow-up for live table rows and strings overrides found wrong (ISSUES.json: `[{key, issue}]`). A key with a strings
  override is fixed there (the text players see; its note gets `was: <old> | <why>`), other keys in the workspace table.
  A Sonnet fixer per chunk of about 5 lines, a Sonnet refuter per fix. A fix must keep the markup, placeholders and line
  breaks of the English it replaces. The scene lines showing the same text follow: exactly, or without the markup for a
  line keyed by the Chinese without it, and only where every row and override with that Chinese agrees. `--arbiter`
  takes `{"reject": {id: why}, "use": {id: text}}`. Chunks in `scene_audit/rowfix/` (`--dir` for another folder).
  `apply --edits FILE` applies exact swaps (below) with the same checks; `--rulings FILE` also swaps the ruled forms into
  the scene lines players can still see (never the audit's dead lines). The workflow's `termOnly: true` makes the fixer
  change only the ruled term.

## Known limitations (maintainer flows; none can ship OverLlm text or change what players see)

Found by the fifth review round and left as they are:

- `source` lists every row re-recorded since the previous dump as `revised_before_source`, including rows that were
  revised correctly for the previous update. Only restamp the rows you actually revised for the new game text.
- A second edit pass over rows that are out of date makes the first pass's `--keep-record` listing stale. Restore
  records from the newest listing.
- If a key has two loadable scene lines with different values, `scene_hygiene.py` cannot fix it, and its publish exits 3.
  Fix the duplicate by hand.
- A malformed `--keep-record` listing given to an apply tool is only caught after the tool's live write. The tool then
  exits 3 without publishing, and a rerun recovers.
- A scene file that is mostly LF with a single CRLF line is reported at lines 1-2. Normalise its line ends.
- Running `source` a second time with the same dump drops the `revised_before_source` group.
- The folder scan catches accidental inclusion, not deliberate hiding (see above).
